# Установка на сервер 2 vCPU / 2 ГБ / 40 ГБ

Эта инструкция относится к **`compose.production.yaml`**: готовые образы, один PostgreSQL с четырьмя отдельными базами, четыре API и Nginx. Локальный переводчик отключён. Русские названия, ручной английский перевод, уведомления, очереди, вопросы, TOTP и офлайн-расписание сохраняются.

**НЕ ПРОВЕРЕНО НА РЕАЛЬНОЙ TIMEWEB 2 GB VM.** Проверки Docker в GitHub Actions и их ограничения описаны в [отчёте](PRODUCTION_VALIDATION_RU.md). Лимиты контейнеров не являются измерением свободной памяти вашего сервера.

Обычный `compose.yaml` остаётся вариантом для разработки и существующих установок с четырьмя PostgreSQL. Не объединяйте два файла через несколько `-f`: новый профиль самостоятельный и использует отдельный том `campus-flow-production_production_data`.

## 1. Что нужно до установки

- Linux x86-64, Python 3, Git, Docker Engine и Compose v2 с поддержкой `up --wait`.
- Домен, HTTPS на внешнем Caddy/Nginx, доступ администратора сервера к Docker.
- Не менее 3 ГиБ свободного диска перед обновлением; дополнительно место для полного бэкапа всех баз. Скрипт проверяет оценку размера копии. Если Docker и репозиторий находятся на разных дисках, проверьте оба.
- Полный SHA успешно опубликованной версии: **40 шестнадцатеричных символов**, одинаковый для API и web.

На сервере не нужны Node.js, `npm ci`, установка Python-зависимостей приложения или сборка Docker-образов. Python-скрипты обслуживания используют стандартную библиотеку.

Инструкции установки: [Docker Engine](https://docs.docker.com/engine/install/), [Compose plugin](https://docs.docker.com/compose/install/linux/). Затем проверьте:

```bash
docker version
docker compose version
python3 --version
free -h
df -h
```

## 2. Откуда брать образы и SHA

Workflow **Publish verified production images** публикует:

```text
ghcr.io/saitwors/campus-flow-api:<полный SHA>
ghcr.io/saitwors/campus-flow-web:<тот же SHA>
```

Публикация запускается после успешного **всего** workflow **Campus Flow verification** для `push` в `main`. Код PR не получает право публикации пакетов. Повторный запуск не перезаписывает уже существующий SHA-тег. В образах есть OCI revision/date, metadata схем и provenance/SBOM.

Пока PR не слит и workflow публикации не завершился, **не считайте образы доступными**. SHA PR и SHA merge-коммита могут различаться. Возьмите SHA именно из успешной публикации на вкладке Actions, убедитесь, что завершились обе задачи `api` и `web`.

Публичные пакеты GHCR скачиваются анонимно. Видимость репозитория и пакета задаётся отдельно: после первой публикации владелец проверяет доступность пакетов. Для закрытых пакетов используйте личный токен с минимальным правом `read:packages`, передавая его через `docker login ghcr.io --password-stdin`. Не записывайте токен в команду, Git или `.env.production`. [Правила GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

Код скриптов/Compose должен соответствовать устанавливаемому релизу. В новой папке:

```bash
git clone https://github.com/SaitWors/campus-flow.git
cd campus-flow
git fetch origin
# Вместо PLACEHOLDER вставьте SHA успешной публикации.
git switch --detach PLACEHOLDER
```

## 3. Конфигурация

Создайте `.env.production` из `.env.production.example`, если его ещё нет. Не заменяйте заполненный файл примером.

```bash
test -e .env.production || cp .env.production.example .env.production
chmod 600 .env.production
```

Заполните локальным редактором:

| Поле | Значение |
| --- | --- |
| `IMAGE_TAG` | Полный SHA опубликованного релиза |
| `IMAGE_REPOSITORY` | `ghcr.io/saitwors/campus-flow` |
| `APP_ORIGIN` | `https://mcg-mtuci.ru` либо ваш действующий домен, без пути |
| `COOKIE_SECURE` | `true` |
| `HTTP_PORT` | `8080`, доступен только через `127.0.0.1` |
| Пять `*_PASSWORD` | Пять разных случайных значений, минимум 32 URL-safe символа |
| `INTERNAL_TOKEN` | Существующий ключ при переносе; случайный ключ при первой установке |
| `SETUP_KEY` | Существующий ключ при переносе; случайный ключ при первой установке |
| `VAPID_SUBJECT` | HTTPS-адрес сайта либо контактный `mailto:` |

Для генерации одного случайного значения используйте `openssl rand -hex 32`. Повторите отдельно для каждого нового секрета. Пароли баз в этом профиле допускают только буквы, цифры, `_` и `-`, чтобы не требовалось URL-кодирование.

**При переносе сначала скопируйте прежние `INTERNAL_TOKEN` и `SETUP_KEY` из используемого `.env`.** Новый INTERNAL_TOKEN нарушит проверку старых сеансов и расшифровку TOTP. VAPID-пара находится в базе notifications и переносится вместе с ней. Пароли новых PostgreSQL-ролей могут отличаться от старых.

Переменные shell имеют приоритет над `.env.production`; не запускайте обслуживание из окружения с посторонними `IMAGE_TAG`, `APP_ORIGIN` или паролями. Рабочую конфигурацию скрипт проверяет без вывода секретов:

```bash
python3 scripts/production.py validate
```

Незаполненный SHA, повторяющиеся/слабые DB-пароли, небезопасные права файла, публичный порт API/БД, отключённые Secure-cookie или отсутствие лимитов остановят проверку. Флаг `--disposable` предназначен исключительно для новых тестовых проектов; для реального сайта он не нужен.

## 4. Первая установка на пустой сервер

```bash
bash scripts/deploy_production.sh
```

Скрипт проверяет конфигурацию и диск, скачивает образы, сверяет их SHA/схемы, запускает контейнеры и ждёт healthchecks. Затем выполняет только проверки чтения. При повторной установке существующие базы сначала резервируются с остановленными API/воркерами.

После успешного запуска:

```bash
python3 scripts/prod_smoke.py --base-url http://127.0.0.1:8080
bash scripts/diagnose_production.sh
bash scripts/check_timeweb40_budget.sh
```

Первого администратора создайте через сайт с `SETUP_KEY`. Готового аккаунта или настоящего расписания в новой базе нет.

## 5. Перенос существующей установки с четырёх PostgreSQL

Перенос требует окна обслуживания. Сначала сохраните независимую копию прежних баз и `.env` вне VM. Новый профиль не переиспользует старые тома и не удаляет их.

1. Оставьте прежнюю установку запущенной. Уточните её Compose project через `docker compose ls`; по умолчанию это `campus-flow`.
2. Подготовьте новый `.env.production` с прежними INTERNAL_TOKEN/SETUP_KEY. Существующий `.env` тоже должен иметь права `600`.
3. Если старый compose находится в другом checkout, укажите его абсолютный путь. Не запускайте новый production-код поверх старых томов до копирования.
4. Запустите из каталога новой версии:

```bash
bash scripts/migrate_four_dbs_to_single_postgres.sh \
  --source-env /opt/campus-flow-old/.env \
  --source-compose /opt/campus-flow-old/compose.yaml \
  --source-project campus-flow
```

Для прежней установки в текущем каталоге достаточно `bash scripts/migrate_four_dbs_to_single_postgres.sh`: пути по умолчанию `.env` и `compose.yaml`. Введите `MIGRATE` после проверки сообщения.

Скрипт проверяет доступность всех четырёх источников, разные имена проектов и пустое назначение. Загружает образы и запускает новую БД, затем приостанавливает старые web/API, делает четыре `pg_dump -Fc`, сохраняет контрольные суммы, версии схем, число и отпечаток строк каждой таблицы. Восстановление выполняется под каждой отдельной ролью. Данные сравниваются **до** запуска миграций приложения, затем проверяются новые версии схем.

При ошибке импорта старая установка возобновляется; неполное назначение остаётся закрытым. При успехе старые API остаются остановленными, новые API готовы, новый web ещё не открыт. Исходные тома сохраняются. Не пытайтесь повторно импортировать в непустое назначение: сначала разберите причину предыдущего результата.

Завершите переключение:

```bash
bash scripts/deploy_production.sh
bash scripts/check_timeweb40_budget.sh
```

Проверьте вход существующим пользователем, расписание, вопросы, уведомления и очередь. Старые БД можно остановить после успешной проверки, сохраняя тома:

```bash
docker compose --env-file /opt/campus-flow-old/.env \
  -f /opt/campus-flow-old/compose.yaml --project-name campus-flow \
  stop auth-db schedule-db queue-db notifications-db
```

Если раньше включали переводчик, отдельно остановите его в старом проекте. Не оставляйте старые воркеры работающими после переключения. До приёмки нового профиля сохраните прежний checkout, `.env` и все тома. После появления новых записей в новом сайте возврат к старым томам потеряет эти новые изменения — это уже отдельное восстановление, а не простая смена адреса.

## 6. HTTPS и сеть

Во внешнем Caddy достаточно блока:

```caddyfile
mcg-mtuci.ru {
    reverse_proxy 127.0.0.1:8080
}
```

DNS A-запись домена должна указывать на выбранный сервер. Открыты наружу только HTTPS/HTTP для TLS и разрешённый вам SSH. Порты PostgreSQL и API не публикуются. `data_net` — внутренняя сеть Docker. Не меняйте привязку web на `0.0.0.0`: [публикация Docker-портов требует отдельного внимания к firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

Перед перезагрузкой проверьте конфигурацию установленного Caddy (`caddy validate --config /etc/caddy/Caddyfile`). Для другого домена одновременно исправьте DNS, внешний прокси, APP_ORIGIN и VAPID_SUBJECT. Приложение не доверяет произвольным proxy headers.

## 7. Обновление и откат

Для обновления выберите новый успешно опубликованный SHA, получите соответствующий checkout и сохраните существующие секреты. Выполните:

```bash
bash scripts/deploy_production.sh --image-tag PLACEHOLDER
```

При существующей базе скрипт делает полную копию до запуска новой версии. SHA и схемы образов проверяются **до остановки** сайта. После healthchecks и проверок чтения новый IMAGE_TAG атомарно сохраняется в `.env.production`; предыдущий SHA и путь к копии — в `.production/<project>/deployment.json`. Ошибка скачивания не останавливает прежний сайт. Ошибка уже начавшейся миграции требует диагностики; автоматический откат схем не выполняется.

Для отката на предыдущие совместимые образы:

```bash
bash scripts/rollback_production.sh
# Либо явно:
bash scripts/rollback_production.sh --image-tag PLACEHOLDER
```

Введите `ROLLBACK`. Скрипт сравнит схемы живых баз с metadata целевого образа до изменения данных, сохранит резервную копию и после успешной проверки обновит IMAGE_TAG. После нескольких последовательных обновлений надёжнее указать нужный SHA явно.

**PR3 → PR2 нельзя считать совместимым откатом образа.** В PR3 auth/schedule имеют схему 3, queue/notifications — 2. Для возврата к PR2 нужны его код, исходная схема 2 и соответствующий полный бэкап/старые тома. Это возвращает данные к моменту копии. Штатный production rollback не запускает старый образ на неизвестной ему схеме.

## 8. Резервные копии и восстановление

```bash
bash scripts/backup_production.sh
```

Копия создаётся в `backups/production-<UTC>/`: четыре dump-файла, `config.env`, `effective-config.json`, `manifest.json`, маркер `COMPLETE`. Во время копирования web и все писатели остановлены для согласованности между базами; затем запускаются только ранее работавшие контейнеры. Копия без COMPLETE считается незавершённой.

**Копия содержит персональные данные, хеши паролей, VAPID и ключи конфигурации.** Она приватная по правам Linux, но не зашифрована самим скриптом. Переносите её целиком в защищённое хранилище вне VM, сохраняя ключ шифрования хранилища отдельно. Права `600/700` не заменяют шифрование.

Проверка восстановления в отдельных временных базах, без замены рабочих данных:

```bash
python3 scripts/production.py test-restore --backup backups/production-PLACEHOLDER
```

После проверки временные базы удаляются. Скрипт сравнивает схемы, число и отпечатки всех строк, а не только успешное завершение pg_restore.

Замена рабочих баз копией:

```bash
bash scripts/restore_production.sh --backup backups/production-PLACEHOLDER
```

Введите `RESTORE`. Контрольные суммы, файлы, версии схем и прежний INTERNAL_TOKEN проверяются до остановки и изменения БД. Перед заменой создаётся ещё одна полная копия текущего состояния. Если импорт не завершён, приложение остаётся остановленным: исправьте причину и повторите восстановление из проверенной копии, не открывайте частичные данные пользователям.

При полной потере VM сначала получите прежний релиз и `.env.production` с тем же INTERNAL_TOKEN, выполните пустую установку, верните каталог копии, затем выполните restore. Новые пароли PostgreSQL должны соответствовать конфигурации новой установки. Для неподдерживаемой версии схемы используйте соответствующий релиз; скрипт не понижает версии автоматически.

Скрипты блокируют параллельные операции обслуживания одного проекта на этой машине. Не запускайте одновременно ручной SQL/Compose или обслуживание из другой копии репозитория.

## 9. Память и диск

| Контейнер | Потолок RAM, МиБ |
| --- | ---: |
| PostgreSQL | 384 |
| auth | 160 |
| schedule | 224 |
| queue | 160 |
| notifications | 192 |
| web | 64 |
| **Сумма** | **1184** |

Остаток нужен ОС, Docker, HTTPS-прокси и файловому кешу. CPU-лимиты ограничивают отдельные контейнеры, а не обещают отсутствие конкуренции за два ядра. Логи ограничены `10m × 3` на контейнер (около 180 МБ суммарно для шести контейнеров), журналы ОС контролируются отдельно.

PostgreSQL: shared_buffers 192 МБ, work_mem 2 МБ на операцию, maintenance_work_mem 64 МБ, autovacuum_work_mem 16 МБ, максимум 30 соединений, JIT отключён. Каждый API: 2 постоянных + до 2 дополнительных соединений. Пароли сохраняют прежние параметры Argon2; auth допускает только одно одновременное тяжёлое вычисление, ожидающие запросы получают 429 по таймауту.

Держите предыдущую рабочую пару образов и проверенную копию до приёмки обновления. Для диска 40 ГБ начальная политика — несколько ежедневных копий и одна недельная **после проверки фактического размера**; важные копии храните вне VM. Скрипты ничего автоматически не удаляют. Перед ручной очисткой посмотрите `docker system df` и размеры `backups`, выберите конкретные неиспользуемые образы/старые копии. Не удаляйте тома и текущую/предыдущую пару образов для освобождения места.

Swap порядка 2 ГБ можно настроить отдельно как аварийный запас, если файловая система и политика сервера это допускают. Он не увеличивает доступную физическую память. Проверяйте `swapon --show`, `free -h`, `vmstat 1 10`; устойчивые `si/so`, OOM или высокая задержка требуют уменьшения нагрузки либо большего сервера. Скрипты swap не создают.

## 10. Диагностика

```bash
bash scripts/diagnose_production.sh
bash scripts/check_timeweb40_budget.sh
curl --fail https://mcg-mtuci.ru/version
curl --fail https://mcg-mtuci.ru/api/auth/version
```

Диагностика показывает ps/stats, память/диск, количество перезапусков, OOM, health и разрешённые поля структурированных журналов. Пути запроса пишутся как шаблоны маршрутов, без query, cookie, Authorization и тела. Ответы API содержат X-Request-ID для сопоставления запроса с журналом. `/version` содержит только build/commit/schema, без конфигурации и секретов.

`check_timeweb40_budget.sh` проверяет уже работающую установку: применённые лимиты, все healthchecks, отсутствие OOM/перезапусков, изоляцию ролей, публичные GET-проверки. Он не создаёт пользователей или тестовые пары. Записывающие сценарии выполняются только в отдельной CI-задаче на одноразовых данных. Это короткая функциональная проверка, не продолжительное нагрузочное испытание.

При ошибке подробный stderr команды сохраняется приватно в `.production/last-error.log`. Не публикуйте его, `.env`, дампы или `docker inspect` целиком; они могут содержать чувствительные значения. Сначала прочитайте локально и выделите причину без данных пользователей.

Основания настроек: [ресурсы Compose](https://docs.docker.com/reference/compose-file/services/), [ограничения Docker и swap](https://docs.docker.com/engine/containers/resource_constraints/), [память PostgreSQL 17](https://www.postgresql.org/docs/17/runtime-config-resource.html). Эти значения выбраны для этого приложения и требуют наблюдения на реальной VM.
