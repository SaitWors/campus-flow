# Размещение Campus Flow на сервере друга

Актуальный вариант после отказа от Timeweb: сервер **95.131.149.248**. Эта инструкция не устанавливает приложение на сервер автоматически и не меняет DNS.

В последней переписке указан домен **msg-mtuci.ru**. В прежнем обсуждении был **mcg-mtuci.ru** — это разные домены. Ниже используется msg-mtuci.ru; если в панели регистратора приобретён mcg-mtuci.ru, заменить его в конфигурации и командах на фактический домен. Доступность HTTPS на домене в этой среде не подтверждена.

## Передать Павлу

Репозиторий: https://github.com/SaitWors/campus-flow  
PR2: https://github.com/SaitWors/campus-flow/pull/2  
Ветка до слияния: feat/notifications-mobile-translator

Обычный запуск PR2 **не держит модель переводчика в памяти и не скачивает её**. Работают интерфейс RU/EN, ручные переводы и уже накопленный кеш. Автоперевод новых названий включается отдельно, когда на сервере есть свободная память. Платные внешние API не подключены.

Ориентир для одной учебной группы: 2 vCPU, 2–4 ГБ свободной RAM и 15–25 ГБ свободного диска для стека без модели, образов и небольших БД. Это оценка, не измеренный лимит и не обещание совместимости с уже размещёнными сервисами. Сначала проверить свободные ресурсы на общем сервере. Для опциональной модели оставить дополнительно до 3 ГБ RAM; её контейнер ограничен 3 ГБ и одним CPU. Посмотреть фактическое потребление после запуска через docker stats.

## DNS и HTTPS

В зоне фактического домена:

| Тип | Имя | Значение |
|---|---|---|
| A | @ | 95.131.149.248 |

AAAA добавлять только при наличии настроенного IPv6. Для корневого домена не должно оставаться конфликтующего A/AAAA другого сайта. NS менять не требуется, если записи редактируются у действующего DNS-провайдера.

Проверить с компьютера:

~~~powershell
Resolve-DnsName msg-mtuci.ru -Type A
~~~

На сервере нужны Docker Engine с Compose v2, Git и действующий reverse proxy. Если у Павла уже есть Nginx/Caddy/Traefik для других сайтов, добавить этот домен в существующий proxy. Второй сервер на портах 80/443 запускать не нужно.

Приложение публикует **только 127.0.0.1:8080**. Базы и API наружу не открываются. Если 8080 занят, выбрать свободный локальный порт и одинаково изменить HTTP_PORT и upstream proxy.

Пример для Caddy, установленного на хосте:

~~~caddyfile
msg-mtuci.ru {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8080
}
~~~

У Caddy в Docker адрес 127.0.0.1 относится к самому контейнеру: там требуется общая proxy-сеть и upstream web:8080, спроектированные под существующую конфигурацию Павла. Пример выше предназначен именно для Caddy на хосте.

Для выпуска сертификата A должен указывать на сервер, а 80/443 — доходить до proxy. [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https).

## Первое развёртывание

Запускать из отдельной папки проекта, под пользователем Павла с правом работы с Docker:

~~~bash
git clone --branch feat/notifications-mobile-translator https://github.com/SaitWors/campus-flow.git campus-flow
cd campus-flow
bash scripts/start.sh
~~~

Скрипт создаёт .env с уникальными ключами и поднимает стек на loopback. После слияния PR2 новый clone можно делать из main.

Затем в .env **сохранить сгенерированные секреты**, изменить только адрес и параметры:

~~~dotenv
APP_ORIGIN=https://msg-mtuci.ru
COOKIE_SECURE=true
BIND_ADDRESS=127.0.0.1
HTTP_PORT=8080
PUSH_ENABLED=true
VAPID_SUBJECT=https://msg-mtuci.ru
COMPOSE_PROFILES=
TRANSLATION_WORKER=false
~~~

VAPID_SUBJECT можно заменить на реальный mailto:адрес администратора. Секретный VAPID-ключ сервис создаёт сам в своей БД; его не нужно генерировать на сторонних сайтах или присылать в чат.

Применить настройки:

~~~bash
docker compose up -d --wait --wait-timeout 180
~~~

Настроить HTTPS в существующем proxy. Открыть домен, создать первого администратора с SETUP_KEY из .env. Ключ сообщается только тому, кто создаёт первый аккаунт. Регистрация остальных — по приглашению и подтверждению.

## Обновить установку PR1

До переключения кода сделать бэкап старыми скриптами PR1:

~~~bash
bash scripts/backup.sh
git status --short
git fetch origin
git switch --track origin/feat/notifications-mobile-translator
bash scripts/start.sh
~~~

Если локальная ветка PR2 уже есть, вместо switch --track выбрать её и выполнить git pull --ff-only. Собственные изменения сначала сохранить отдельным коммитом. Команды reset --hard и удаления Docker volumes для обновления не нужны.

start.sh / start.ps1 добавляют отсутствующий NOTIFICATIONS_DB_PASSWORD в существующий .env, сохраняя старые ключи. При ручном docker compose up этот новый пароль необходимо заполнить самостоятельно случайным значением.

Миграция базы queue: версия 1 → 2, добавляется таблица событий. Существующие очереди и места сохраняются. База schedule остаётся версии 2 из PR1. Новая база notifications создаётся отдельно. Поэтому **откат на PR1 требует соответствующей версии кода и полного бэкапа PR1**, а не запуска старого кода поверх новой queue DB.

## Если нужен локальный переводчик

В .env:

~~~dotenv
COMPOSE_PROFILES=translation
TRANSLATION_WORKER=true
~~~

Затем:

~~~bash
docker compose --profile translation up --build -d --wait --wait-timeout 180
~~~

Загружается только **RU → EN 1.9** с фиксированным URL и SHA256. Установщик проверяет направление, версию, целостность архива, повторяет прерванную загрузку до пяти раз и продолжает её с места обрыва при поддержке Range. BuildKit сохраняет частичный файл в кеше между сборками.

Сбой скачивания модели не мешает запуску обычного стека без профиля. Чтобы снова убрать модель из памяти:

~~~bash
docker compose --profile translation stop translator
~~~

И вернуть в .env пустой COMPOSE_PROFILES и TRANSLATION_WORKER=false, затем docker compose up -d. Кеш уже переведённых названий и ручные исправления останутся.

## Проверить после размещения

1. docker compose ps: четыре API, четыре БД и web здоровы. translator присутствует только при включённом профиле.
2. Вход по HTTPS работает; cookie cf_session имеет HttpOnly, Secure и SameSite=Lax.
3. /internal/events возвращает 404, а БД, сервисные порты и переводчик недоступны извне.
4. Староста создаёт тестовое объявление. Оно появляется у студента; студент не может публиковать объявления.
5. Студент включает push и нажимает «Отправить пробное». Для теста временно отключить тихие часы и оставить включённой категорию «Объявления».
6. Закрыть вкладку, опубликовать ещё одно тестовое объявление и проверить доставку на реальном устройстве. iPhone предварительно добавить на главный экран.
7. Проверить выход и повторный вход, отключение устройства, отмену объявления. Тестовые объявления затем отозвать.
8. Запустить новый бэкап и проверить восстановление на отдельной тестовой установке.

Не запускать scripts/smoke.py и scripts/verify_notifications.py на рабочей группе: это тесты с одноразовыми CI-аккаунтами и изменением расписания.

## Сеть и резервные копии

- Снаружи: только 80/443; SSH ограничить правилами сервера и ключами.
- Исходящий HTTPS для notifications: fcm.googleapis.com, updates.push.services.mozilla.com, *.push.apple.com, *.notify.windows.com. Это службы браузеров, не публичный входящий API приложения.
- У переводчика нет исходящего доступа во время работы; загрузка модели выполняется при сборке.
- Docker-публикация может обходить UFW, поэтому сохранять привязку к loopback и проверять доступность портов снаружи. [Docker firewall documentation](https://docs.docker.com/engine/network/packet-filtering-firewalls/).
- Новые backup/restore скрипты включают **четыре** БД, .env, подписки и VAPID-ключ. Копию хранить за пределами сервера с ограниченным доступом.
- Старый трёхбазовый бэкап PR1 восстанавливается старой версией приложения/скриптов на отдельной установке, после чего выполняется обновление. Новые restore-скрипты намеренно требуют notifications.dump и не смешивают наборы.
- Не выполнять docker compose down --volumes на рабочем сервере. SSH-ключи, .env и доступ к регистратору не помещать в репозиторий и сообщения.

Доступы к серверу или DNS для подготовки PR не нужны. Эта инструкция оставляет Павлу выбор proxy и ресурсов общего сервера.
