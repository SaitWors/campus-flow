# Study Hub Implementation Plan

> **For agentic workers:** implement the owned subsystem independently with tests first; root integrates and reviews the complete branch. Use the dispatching-parallel-agents skill for disjoint file ownership.

**Goal:** Deliver the approved daily study hub, remove queues, improve browser and Telegram notifications and backup operations in one reviewable PR.

**Architecture:** Reuse auth/schedule/notifications and their separate databases. Academic data belongs to schedule; personal assignment progress is private. Telegram is an optional worker inside notifications; no new service or broker.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy, PostgreSQL/SQLite, React 19, TypeScript, Vite.

**Spec:** docs/superpowers/specs/2026-10-06-study-hub.md

## Global Constraints
- No timetable import. No queue subsystem or active queue routes.
- RU/EN, existing themes, MFA/CSRF, public calendar/offline privacy remain functional.
- General academic mutations require manager; progress mutation always uses authenticated user id.
- No real bot sends, production changes, merge, or database deletion in this session.
- Secrets only via existing environment configuration; do not log Bot API token or binding codes.
- Existing users and schedules survive migrations; new operations use revision guards.

## Review Focus
- Timezone midnight and cancelled classes must not produce a wrong next class/deadline.
- A second student must never read/write another student's progress or Telegram binding.
- Replayed Telegram update/link must not rebind an account or duplicate stored delivery.
- Expired/inactive/revoked audiences must not receive delayed notifications.
- Old installations/backups with a fourth queue database must have a safe documented upgrade path.
