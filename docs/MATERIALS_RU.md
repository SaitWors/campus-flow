# Материалы предметов

На странице предмета раздел «Материалы» хранит лекции, конспекты, изображения и другие учебные файлы группы. Подтверждённые участники могут искать, просматривать и скачивать материалы. Загружают, редактируют и удаляют материалы только admin, староста (head) и заместитель (deputy). Гостям и неподтверждённым аккаунтам файлы недоступны, в том числе по прямой ссылке.

Руководство выбирает один или несколько файлов; приложение загружает их последовательно. Для каждого материала доступны название, описание и категория «Лекция», «Конспект» или «Другое». Удаление требует подтверждения. Конфликт редактирования предлагает обновить список, чтобы не перезаписать чужие изменения.

По умолчанию один файл ограничен **50 МиБ**, всё хранилище — **5 ГиБ**. Поддерживаются PDF, документы Office/OpenDocument, TXT/MD/CSV, PNG/JPEG/WEBP/GIF/HEIC, ZIP, MP3/M4A/OGG/WAV и MP4/WEBM. HTML, SVG и исполняемые файлы запрещены. Предпросмотр доступен для PNG/JPEG/WEBP/GIF; HEIC и документы скачиваются. Материалы не входят в офлайн-копию расписания.

## Размещение и настройки

Оба Compose-профиля монтируют именованный том `materials_data` только в schedule, по пути `/var/lib/campus/materials`. Контейнер работает с UID/GID **10001:10001**, основной файловой системой только для чтения; каталог тома заранее создан в образе с правами 0700. Новые сервисы не добавляются. Локальный `scripts/dev.py` использует `.dev-data/materials`.

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `MATERIALS_DIR` | `/var/lib/campus/materials` в Compose | Приватный каталог файлов |
| `MATERIAL_MAX_FILE_BYTES` | `52428800` | Лимит одного файла в байтах |
| `MATERIAL_STORAGE_QUOTA_BYTES` | `5368709120` | Общая квота в байтах |

В Compose можно уменьшить лимит файла. Для увеличения свыше 50 МиБ потребуется согласованное изменение обоих прокси; штатный профиль ограничивает загрузку 50 МиБ. Не направляйте `MATERIALS_DIR` внутрь `/tmp`: production `/tmp` — tmpfs на 32 МиБ. Имена на диске — UUID с расширением `.blob`; исходное имя файла хранится только в базе. `.part` — незавершённая загрузка; `.lock` — временный файл блокировки загрузки, который может остаться после аварийного завершения. Только обычные файлы с корректным UUID принимаются как временные; оба вида не включаются в архив.

## HTTPS-прокси

Внутренний Nginx сохраняет общий лимит тела **64 КиБ**. Только точный **POST** `/api/schedule/subjects/{64 строчных hex-символа}/materials` получает лимит **50 МиБ**, `proxy_request_buffering off`, HTTP/1.1 и таймауты 300 секунд. Передаётся сырое тело одного файла, без multipart.

При запуске schedule напрямую используйте `uvicorn services.schedule.main:app --h11-max-incomplete-event-size 65536`: это позволяет принимать максимальные Unicode-метаданные, когда строка запроса приходит частями. Оба Compose-профиля и `scripts/dev.py` задают этот параметр. Описание настройки: [Uvicorn settings](https://www.uvicorn.org/settings/).

Если HTTPS завершает внешний Nginx, ему нужны те же правила для этой загрузки: отдельный лимит 50 МиБ, отсутствие буферизации запроса и таймауты передачи/чтения 300 секунд. Остальным маршрутам оставьте существующий небольшой лимит. Для валидных Unicode-имён и описаний query-строка может занимать около 53 КиБ: задайте `large_client_header_buffers 2 64k` (внутренний gateway уже настроен), сохраняя ограничения метаданных приложения. Параметры запроса и содержимое файлов не включаются в штатные журналы gateway.

Файлы доступны только через авторизованный API; публичного static-каталога нет. Предпросмотр получает изображение с проверкой сессии и `no-store`, затем создаёт временный Blob URL. CSP разрешает `blob:` только для изображений.

## Копии, восстановление и перенос

`backup.sh` / `backup.ps1`, production backup и внешняя SSH-копия включают **materials.tar**, три дампа, конфигурацию, manifest и COMPLETE. Во время создания копии писатели остановлены; размеры и SHA-256 файлов сравниваются с записями таблицы `materials`. Отсутствующий или изменённый файл не позволяет завершить копию. Архив плоский: только обычные UUID.blob, без путей, ссылок и дубликатов.

До остановки восстановления проверяются полнота, INTERNAL_TOKEN, версии схем, контрольные суммы всех файлов и каждого члена materials.tar. В production test-restore материалы извлекаются в отдельный временный каталог на диске, базы — в отдельные временные БД. Рабочий том не заменяется этой проверкой.

Штатный restore сохраняет полную копию текущего состояния, останавливает приложение, размещает проверенные файлы в отдельном staged-каталоге на томе и восстанавливает базы. После проверки записей материал-файлы публикуются атомарными переименованиями, затем запускается приложение. Ошибка импорта сохраняет прежний файловый snapshot; обычная ошибка публикации возвращает уже перемещённые файлы. Приложение остаётся остановленным при любой ошибке. Production restore/test-restore требуют snapshots трёх текущих БД в manifest; локальные копии без snapshots проверяются локальным helper и восстанавливаются локальными restore-скриптами. Исторический дополнительный snapshot queue допускается.

Операции файлового тома используют постоянную `.materials-ops.lock`, приватный ключ и подписанный журнал. Блокировка удерживается всё время приёма архива. После SIGKILL незавершённый приём автоматически очищается следующей операцией только при свободной блокировке, валидном журнале и безопасных обычных файлах внутри принадлежащего операции каталога. Неизвестные каталоги, ссылки и поддельные журналы сохраняются и приводят к отказу; helper не удаляет их вслепую.

Прерванная публикация блокирует новые backup/restore до явного recovery. Остановите приложение и выполните для production:

```bash
docker compose --env-file .env.production -f compose.production.yaml stop web notifications schedule auth
docker compose --env-file .env.production -f compose.production.yaml run --rm --no-deps -T schedule python -m scripts.materials_archive recover /var/lib/campus/materials
```

Для локального Compose используйте те же команды без `--env-file .env.production -f compose.production.yaml`. Recovery не меняет БД: незапубликованный stage отбрасывается, а уже начатая публикация завершается только после проверки нового и прежнего файловых snapshots. Прежние байты остаются в `.recovered-{id}` с подписанной `.recovery.json`; обычные успешные публикации также сохраняют такой предыдущий snapshot. Эти каталоги и служебные файлы не входят в materials.tar, квоту и счётчик живых файлов. После проверенного полного восстановления ненужный `.recovered-{id}` можно целиком удалить при остановленном приложении; не удаляйте служебный ключ или отдельные файлы внутри сохранённого snapshot.

После прерывания импорта БД файловый recovery сам по себе не подтверждает согласованность установки. Держите приложение остановленным до восстановления трёх БД из одной проверенной полной копии и сравнения с её snapshots; сохраните страховочную копию. При неизвестном или повреждённом журнале сохраните том целиком для диагностики, вместо удаления `.restore-*` / `.previous-*` вручную.

Старые manifest-копии без материалов принимаются только для schedule **ниже 5**. Прежние локальные копии без manifest также принимаются лишь после чтения столбца version внутри COPY-блока schema_migrations в выводе pg_restore, проверки структуры дампов и исходного INTERNAL_TOKEN; исторической контрольной суммы в таких копиях нет. Восстановление старой точки очищает позднейшие материал-файлы и новые таблицы, чтобы не смешивать разные состояния.

Перенос установки проверяет архив до создания файловых/DB-томов назначения, затем переносит и базы, и материалы. Источник без material-тома поддерживается только для схем до 5. Исходные тома сохраняются; при ошибке источник возобновляется, неполное назначение остаётся закрытым. Внешняя копия передаёт тот же проверенный архив; автоматического удаления старых копий нет.

Место на диске нужно для живых файлов, выбранной копии, страховочной копии и staged-файлов одновременно. Лимит квоты ограничивает живое хранилище, а не все резервные копии. Следите за фактическим свободным местом.
