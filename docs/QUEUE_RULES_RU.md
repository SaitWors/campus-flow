# Очередь: правила и спорные ситуации

Очередь привязана к **одному конкретному занятию**, а не к предмету целиком. На следующей лабораторной — новая очередь. У лекций очередей нет; у практик они включаются при необходимости.

## Обычный путь

Староста создаёт очередь → открывает запись → студент указывает работу и записывается → с начала пары староста вызывает следующего → отмечает сдачу или отсутствие. Положение в очереди назначает сервер после записи в базу, а не часы или интерфейс компьютера студента.

| Сценарий | Поведение |
| --- | --- |
| Два человека нажали запись почти одновременно | Транзакции упорядочивают записи; у каждого уникальный талон |
| Осталось одно место, записываются двое | Один занимает место; второй получает сообщение о заполнении |
| Один студент нажал дважды | Второе активное место не создаётся |
| Связь пропала после нажатия | Повтор с тем же ключом возвращает текущее состояние без повторного изменения |
| Студент вышел и записался заново | Попадает в конец; старый талон остаётся в истории |
| После выхода пришёл запоздалый повтор старого запроса | Старый запрос не записывает студента повторно |
| Время открытия ещё не наступило | Показаны причина и дата открытия; даже открытая старостой очередь не принимает заранее |
| Лимит уменьшили ниже числа записанных | Сохранение отклоняется; сначала нужно снять участников или дождаться завершения |
| Очередь на паузе | Новая запись и вызов остановлены, места сохранены; уже вызванного можно завершить |
| Текущий студент ещё отвечает | Следующий вызов недоступен |
| Один студент вызван в другой очереди | Одновременный вызов блокируется ограничением базы |
| Первый студент заблокирован или сменил подгруппу | Вызов блокируется; староста снимает его с объяснением |
| «Не пришёл» | Место закрывается с отметкой; можно записаться снова в конец |
| «Работа сдана» | Повторная запись этого студента на эту же пару закрыта |
| Студента уже вызвали, а он нажимает выход | Самостоятельный выход недоступен: староста завершает, пропускает или снимает |
| Староста снимает участника | Обязательна причина; сохраняется история |
| Два руководителя одновременно меняют очередь | Устаревшая версия получает ошибку; нужно обновить данные |
| Не та подгруппа | Запись запрещена; общая пара доступна обеим подгруппам |
| Пара ещё не началась | Записываться можно в разрешённое окно, вызывать студентов ещё нельзя |
| Пара закончилась | Запись и вызов закрываются; активные места переходят в историю с истекшим сроком |

## Переносы и отмены

| Изменение пары | Что происходит с очередью |
| --- | --- |
| Перенос на другую дату / время | Очередь сохраняет идентификатор, участников и порядок; приостанавливается |
| Изменение аудитории, формата или других условий | Очередь приостанавливается до проверки и повторного открытия |
| Статус «Ожидает решения» | Запись и вызов недоступны до подтверждения |
| Отмена | Очередь закрывается, активные места получают отметку отмены |
| Отключение очереди в паре | Активные места закрываются, история остаётся |
| Пару вернули после отмены | Староста открывает очередь заново; студентам требуется новая запись |
| Староста нажал «Закрыть очередь» | Требуется причина; активные места отменяются |
| Недоступен сервис расписания или аккаунтов | Запись и вызов не выполняются до восстановления связи |

Число перед вашим именем — **текущее место**. Номер талона в истории — постоянный номер записи; он может иметь пропуски. Оценка ожидания = число людей впереди × заданные минуты на студента. Это приблизительная оценка, не обещание конкретного времени приёма.

Очередь обновляется в открытой вкладке примерно каждые 4 секунды. В фоновой вкладке опрос прекращается и возобновляется при возвращении. Уведомлений Telegram, браузерных push и голосового вызова в этой версии нет. Состояние «Вас вызвали» видно внутри открытой карточки.

Отображаются до 100 последних завершённых мест очереди; полный журнал действий хранится в базе. Участники видят имена и названия работ. Email доступен руководителям в управлении группой. ФИО в истории фиксируется на момент записи.

## Ограничение согласованности

Внутри одной очереди операции сериализуются блокировкой строки PostgreSQL. Проверка занятия выполняется по HTTP, а изменения расписания также доставляются фоновым обработчиком событий. Это **не общая транзакция между тремя базами**: изменение пары, совпавшее с уже выполняющимся запросом очереди, может быть согласовано после завершения этого запроса. Фоновая сверка и чтение подробностей очереди приводят её к актуальному состоянию. При недоступности расписания новые критические действия блокируются.

Такая модель подходит для группы и не означает строгую глобальную синхронность нескольких сервисов. Для гораздо большего масштаба или строгих межсервисных гарантий нужен отдельный механизм согласования операций.
