# Размещение, копии и восстановление

> Для нового `compose.production.yaml` используйте [инструкцию небольшого сервера](DEPLOY_TIMEWEB40_RU.md) и скрипты `*_production.sh`. Команды ниже относятся к прежнему `compose.yaml` с четырьмя экземплярами PostgreSQL.

> **PR2:** уведомления, колокольчик, мобильное PWA и отдельный сервис объявлений. [Уведомления](NOTIFICATIONS_RU.md) · [Установка на сервер друга](DEPLOY_FRIEND_RU.md). Обычный запуск теперь без модели; для автоперевода включить COMPOSE_PROFILES=translation и TRANSLATION_WORKER=true. Новые бэкапы включают четыре БД.

## Обычные команды

Выполняйте из папки с `compose.yaml`.

```bash
docker compose ps
docker compose logs --tail 100
docker compose logs -f queue
docker compose stop
docker compose up -d --wait
docker compose up --build -d --wait
```

`stop` останавливает контейнеры без удаления данных. `down` удаляет контейнеры и сеть, но сохраняет именованные тома. **`docker compose down --volumes` удаляет базы** — не используйте его для обычного обновления.

Базы — в томах `auth_data`, `schedule_data`, `queue_data` проекта Compose. Копирование только папки с исходниками не копирует базы.

## Открыть с других устройств

По умолчанию порт привязан к `127.0.0.1`, поэтому сайт доступен только на компьютере/сервере, где запущен. Для краткой проверки в доверенной локальной сети можно выставить:

```dotenv
BIND_ADDRESS=0.0.0.0
HTTP_PORT=8080
APP_ORIGIN=http://192.168.1.50:8080
COOKIE_SECURE=false
```

Замените IP на адрес своего компьютера, разрешите входящий TCP-порт 8080 в локальном брандмауэре и выполните `docker compose up -d`. Участники открывают именно этот IP. Если нужен вход с нескольких адресов, перечислите точные origin через запятую: `http://localhost:8080,http://192.168.1.50:8080`. Протокол и порт имеют значение.

Для постоянной работы группы предпочтителен Linux-сервер с доменом и HTTPS. HTTP не шифрует пароли и содержимое запросов.

## Домен и HTTPS

Пример: домен `schedule.example.org` направлен A/AAAA-записью на ваш сервер. На хосте установлен [Caddy](https://caddyserver.com/docs/automatic-https). В конфигурации приложения:

```dotenv
APP_ORIGIN=https://schedule.example.org
BIND_ADDRESS=127.0.0.1
HTTP_PORT=8080
COOKIE_SECURE=true
```

Замените домен своим, не используйте пример буквально. `Caddyfile` на том же хосте:

```caddyfile
schedule.example.org {
    reverse_proxy 127.0.0.1:8080
}
```

Установите Caddy по его документации, проверьте конфигурацию и перезагрузите сервис. Порты 80/443 должны быть доступны, DNS должен указывать на сервер. После изменения `.env` выполните `docker compose up -d --wait`. Не включайте Secure-cookie при входе по обычному HTTP.

Если Caddy работает в отдельном контейнере, его `127.0.0.1` указывает внутрь того контейнера; используйте отдельную согласованную сеть или вариант с Caddy на хосте, описанный выше. Не публикуйте порты баз и API.

За внешним прокси текущий Nginx использует адрес непосредственного прокси для общего IP-лимита. Лимит входа также разделён по аккаунтам. Для большой аудитории настройте доверенные прокси явно, не доверяя произвольному клиентскому `X-Real-IP`.

## Резервное копирование

Перед обновлением создайте копию. На время копирования скрипт останавливает web и четыре сервиса приложения, оставляя базы доступными. Это позволяет последовательно снять согласованный комплект четырёх баз без пользовательских записей и фоновых изменений очередей.

**Windows, PowerShell:**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\backup.ps1
```

**Linux:**

```bash
bash scripts/backup.sh
```

Результат: `backups/ДАТАВРЕМЯ/`, четыре файла `.dump`, `config.env` и маркер `COMPLETE`. Если маркера нет, копия не закончена. Приложение запускается обратно после успешного копирования и при ошибке дампа. Проверьте `docker compose ps`.

Перенесите весь комплект на другое устройство. Он содержит учётные данные и секреты; не публикуйте его в GitHub или чат группы. Отдельный ZIP исходников не заменяет резервную копию. Автоматическое расписание бэкапов не настроено; при необходимости вызывайте скрипт через планировщик хоста, без пересекающихся запусков.

## Восстановление на той же установке

Сначала сохраните свежую копию текущих данных. Убедитесь, что выбран правильный комплект. Восстановление заменяет все четыре базы, а не добавляет недостающие записи.

**Windows:**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\restore.ps1 -BackupPath .\backups\20260913T220000Z
```

**Linux:**

```bash
bash scripts/restore.sh backups/20260913T220000Z
```

Подставьте фактическое имя своей папки. Скрипт просит набрать `RESTORE`, останавливает приложение и восстанавливает базы. При ошибке приложение остаётся остановленным, чтобы не работать с частично восстановленным комплектом. Исправьте причину и восстановите все четыре базы перед запуском.

На существующей установке `.env` автоматически не заменяется: в нём должны оставаться пароли доступа к текущим контейнерам баз. Дамп PostgreSQL не меняет пароли ролей сервера. Поэтому простая подмена `.env` другим комплектом без согласования паролей может сломать доступ.

## Перенос на новый сервер

1. Скопируйте исходники той версии, с которой сделана резервная копия.
2. Скопируйте `config.env` из комплекта в `.env` в корне нового проекта.
3. Исправьте только публичный адрес, привязку порта и Secure-cookie под новый домен; сохраните ключи и пароли баз.
4. Убедитесь, что на новом хосте у проекта нет старых томов с другими паролями. Если там уже есть установка, используйте отдельное имя Compose-проекта (`docker compose -p campus-flow-recovery ...`) и отдельный порт, последовательно применяя это имя ко всем командам.
5. Запустите `docker compose up --build -d --wait`, не регистрируйтесь и не добавляйте данные.
6. Поместите комплект в `backups/` и выполните восстановление.
7. Войдите под аккаунтом из копии и проверьте расписание, роли, историю очередей.

Скрипты по умолчанию работают с именем `campus-flow` из compose.yaml. Для нескольких установок задайте `COMPOSE_PROJECT_NAME` в окружении для каждого запуска, включая start/backup/restore. Это предотвращает обращение к чужим томам. Отдельная директория сама по себе не меняет фиксированное имя проекта.

## Если не запускается

| Симптом | Что проверить |
| --- | --- |
| `docker` не найден | Установлен ли Docker и открыт ли новый терминал после установки |
| Docker daemon недоступен | Запущен ли Docker Desktop / сервис Docker |
| Windows containers вместо Linux | Переключите Docker Desktop на Linux containers |
| Порт 8080 занят | Измените `HTTP_PORT`, одновременно исправьте `APP_ORIGIN` |
| `Run setup` / отсутствуют переменные | Запускайте START_WINDOWS.cmd или scripts/start.sh; пустой `.env.example` не подходит |
| Скрипт нашёл уже существующий, но пустой `.env` | Он специально не перезаписывает конфигурацию; восстановите корректный файл или удалите только пустой файл перед самым первым запуском |
| Не принимаются ключ/пароль администратора | `SETUP_KEY` — ключ настройки, не пароль аккаунта; пароль вы выбираете в форме |
| После смены домена нельзя сохранить | Сверьте точный `APP_ORIGIN`, затем пересоздайте сервисы командой `docker compose up -d` |
| После входа снова страница входа | Проверьте `COOKIE_SECURE`: true требует HTTPS; проверьте cookies браузера |
| Аккаунт ожидает подтверждения | Староста/заместитель/администратор должен подтвердить заявку |
| Очередь заблокирована после редактирования | Откройте карточку, проверьте условия и снова откройте очередь |
| Ошибка версии данных | Другой человек уже сохранил изменение; обновите и повторите с актуальными полями |
| После смены DB-паролей контейнеры unhealthy | Пароли в существующих томах не меняются через POSTGRES_PASSWORD; верните прежний `.env` или выполните согласованную смену роли PostgreSQL |
| Сборка не скачивает образы/пакеты | Проверьте доступ хоста к Docker Hub, npm и PyPI; смотрите конкретную ошибку сборки |

Не присылайте целиком `.env`, дампы или вывод `docker compose config` с реальными ключами. Для диагностики обычно достаточно `docker compose ps` и последних строк логов ошибки.
